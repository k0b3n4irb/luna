# Testing & validation

Luna's accuracy is held in place by **two complementary tiers** of automated
tests (a third, `luna test`, puts the same machinery in homebrew developers'
hands), plus the differential harness from the [previous chapter](differential.md).
The exact commands and file locations live with the code (see the repository's
`tests/` directories and contributing notes); this chapter describes *what* is
validated and *why* it is trustworthy.

## Tier 1 — per-instruction CPU suites (independent oracle)

Both CPU cores are checked against **exhaustive single-instruction
state-transition vectors** — ten thousand cases per opcode for the 65C816
(in each of its two modes, native and emulation), one thousand for the
SPC700 — covering every addressing mode and flag combination. Each case sets the processor to a
known state, runs one instruction, and asserts the resulting registers, flags
and memory.

These vectors are an **independent correctness oracle**: written by a third
party, they do not share Luna's code. They are *not* hardware captures — the
vectors are generated by a software model, not recorded on a console, so
"hardware" is a word this page keeps for measurements made on a console.
Current state:

| Core | States passing / in the dataset | Not counted as passing |
|---|---|---|
| 65C816 | 5,079,754 / 5,120,000 | 40,000 states of the four `MVN`/`MVP` files are not run; 246 states contradict the dataset by choice (Luna follows ares, Mesen2 and a console-tested third-party test ROM; listed as `CONTESTED_STATE` in the harness) |
| SPC700 | 256,000 / 256,000 | none |

The datasets are large, so they are fetched on demand and gated in their own CI
job rather than run on every `cargo test`.

## Tier 2 — full-system golden ROM tests (regression baselines)

End-to-end homebrew hardware-test ROMs exercise the *whole* machine — CPU, PPU
and bus together. Each test boots a ROM, runs it until the framebuffer settles
(or to a fixed, deterministic instruction count for animated scenes), and
asserts a hash of the result:

- **Display ROMs** hash the 256×224 framebuffer (256×239 under overscan) — opcode result screens (every
  group renders its all-PASS table), background modes, hi-colour blending,
  windows, Mode 7, and mosaic.
- **Audio ROMs** play music or sound effects rather than draw, so they hash the
  APU's 32 kHz PCM output instead of the framebuffer.

Unlike the Tier-1 vectors, these hashes are captured from **Luna's own output**,
so they are **regression baselines**, not an independent oracle. Each ROM ships
a reference picture (an emulator capture of unverified provenance, not a console
photograph). A second group of tests compares Luna's stable picture with it pixel by
pixel at tolerance 0: 22 ROMs are exact, 21 are within one LSB of colour conversion (a
named class, bounded at 1), 12 are listed exceptions with their reason, and a listed
exception that starts to match fails until it is promoted (details in
`docs/test_corpora.md`). A baseline is re-blessed after any intended render change.

The ROM corpus is **not vendored** — it is fetched on demand and the tests
skip cleanly if it is absent, so a plain build never depends on it.

### A nuance worth knowing: the video standard

The video standard is chosen per family. The **PPU demos run as PAL**, the
convention of the `twvd/siena` suite and of krom's reference captures. The
**CPU test family runs as NTSC**: each of those ROMs waits for one vblank, then
writes its whole result table in a single burst. In PAL the burst overruns
vblank and the table is truncated mid-row; in NTSC the full table lands. Mesen2
agrees on both: its PAL screen is pixel-identical to Luna's truncated one, and
in NTSC both render the full all-PASS table. (The family used to run as PAL,
on the opposite theory, calibrated against an old boot that ran too fast.)

## Why two tiers

The per-instruction suites prove each opcode is right in isolation but say
nothing about how the subsystems interact. The golden ROMs prove the *system*
renders correctly but, being Luna's own output, can only catch *regressions*.
Together — plus the differential harness for timing — they cover correctness
from the single instruction up to the whole frame.

## Tier 3 — user-facing: `luna test` (homebrew CI)

The first two tiers test *luna*; `luna test` lets homebrew developers test
*their game* with the same machinery — TOML manifests asserting on symbols,
the SDK assert/log channels and displayed-frame hashes, run in-process
through `luna-api` with a CI exit-code contract. See
[Developing homebrew with luna](../using/homebrew-ci.md).

## `ORACLE.json` — which oracles validated a commit

A green check mark does not say *what* it was green against. `ORACLE.json` does:
a small, versioned file (`schema: 1`) that CI **writes from the real results of
the gates**, never by hand (`tools/oracle-json.py`, stdlib only, with its
tests in `tools/test_oracle_json.py`). Any consumer can then say *"validated on
2026-11-08 at `e55389f` by the 65C816 and SPC700 Tom Harte suites, the golden
ROMs and the doc check; NOT proven: …"* without re-reading the workflows.

| Field | Meaning |
|---|---|
| `schema` | format version, `1` |
| `generated_at` | UTC time the file was written |
| `commit` | full sha the gates ran on |
| `luna_version` | the workspace version at that commit |
| `gates[]` | one entry per gate: `name`, `workflow` (file / job), `result` (`pass`, `fail` or `skipped`), `counts`, `run_url` (the Actions run, or `local`) |
| `not_proven` | a **fixed** list kept in the script: what no gate proves, whatever its colour (the Tom Harte vectors come from a software model and not from a console; the PNG / hash goldens are luna's own output or captures of unverified provenance; the contested `(dp,X)` states follow ares and Mesen2; coprocessors and the absolute audio level are not calibrated on a console) |
| `core_code_commit` | the last commit that touched the CPU / APU core code (`core_code_paths` lists it) |

The gates are `tom-harte-65816` and `tom-harte-spc700` (the *Tom Harte CPU
suites* workflow), `snes-test-roms` (the golden ROM suite) and `doc-drift`
(`ci.yml`). The Tom Harte `counts` are the report the harness already prints,
parsed: `states_passed` / `states_total`, `contested` (the 246 states of
`CONTESTED_STATE`, read from the harness source), `not_run` (the `MVN`/`MVP`
states), and the cycle-count and bus-trace matches. A gate is `pass` only if
the test verdict is green **and** the numbers sit exactly on the baseline (a
`Fail` count other than the contested states, a panic or a cycle mismatch is
`fail` even if the harness was run without its strict switch); a sampled run is
`skipped`, it is not a gate. A CI outcome of `failure` or `cancelled` always
gives `fail`.

**Where the file comes from.** Each workflow uploads it as the artifact
`oracle-json`: the `Tom Harte CPU suites` workflow (the Tom Harte gates; the
others read `skipped` there) and `ci.yml` (golden suite and doc check; the Tom
Harte gates read `skipped`). A gate counts only where its `result` is not
`skipped`. The Tom Harte workflow does not run on every push, only when the CPU
cores change (and weekly): a commit without a run **inherits the last run on
the same core code**. Compare `core_code_commit` of the commit you ask about
with the `core_code_commit` (and `commit`) of the latest Tom Harte file: if they
are equal, no CPU / APU code moved in between and that run still speaks for the
commit. Whether a file is too old to trust is the consumer's call; the file
carries `generated_at` and `commit` for that.

**Locally**, for a build you are about to hand over, keep the logs of the runs
and let the script read them (every input is optional; the gates without a log
are `skipped`):

```bash
LUNA_TOM_HARTE_REQUIRE=1 cargo test -p luna-cpu-65c816 --test tom_harte --release -- --ignored --nocapture > th816.log 2>&1
LUNA_TOM_HARTE_REQUIRE=1 cargo test -p luna-cpu-spc700 --test tom_harte --release -- --ignored --nocapture > thspc.log 2>&1
tools/oracle-json.py --tom-harte-65816 th816.log --tom-harte-spc700 thspc.log -o ORACLE.json
```

The generated file is never committed (it is in `.gitignore`).
